# ADR-0001：先建设 Harness，再选择业务技术栈

- 状态：Accepted
- 日期：2026-07-29

## 背景

研究报告已经定义了完整愿景，但产品 PRD、领域契约、数据可用性和 MVP 边界仍需逐步验证。若此时直接选择微服务、数据库或多 Agent 框架，容易把尚未验证的认知模型固化为昂贵架构。

## 决策

第一阶段先建设仓库内 Harness：

- `AGENTS.md` 作为唯一 Agent 规范源
- 研究、架构、状态、任务、评估和模板分层
- 先定义 Market Cognition Frame、Evidence Item 和 Forecast Contract
- 使用无第三方依赖的校验脚本保证工程完整性
- 业务实现按 MVP 切片后再通过 ADR 选择技术栈

## 结果

正面：

- 不同 Agent 和会话可以稳定接续。
- 研究事实、工程推断和产品决策更容易审计。
- 可以先验证输出契约，再决定平台复杂度。

代价：

- 初期交付以文档、schema 和离线原型为主。
- 具体业务代码与部署方案需要后续任务补充。

## 被否决的方案

- 立即生成完整微服务骨架：范围过大，领域尚未稳定。
- 仅保留一份长研究报告：无法驱动可重复实施和验证。
- 为每个工具复制一套规则：容易产生规范漂移。
