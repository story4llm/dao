# Harness 工作流

本工作流吸收“原型—计划—实现—人工迭代—异质模型复核—提交”的方法，但把金融研究中的时点、证据和概率质量加入每一步。

## 1. Prototype：让问题可见

先产出最小样例，而不是直接建设完整平台。样例可以是一张市场认知卡、一个 JSON 契约、一段回放结果或一个交互草图。

原型必须暴露：

- 用户真正要做的决策
- 可用数据和不可用数据
- 情景、失效条件和弃权状态
- 最容易被误读为“交易信号”的部分

原型不是产品承诺，也不进入实盘。

## 2. Plan：把模糊需求变成可验收任务

从 `tasks/TEMPLATE.md` 创建任务文件，回答：

- 要解决的单一问题是什么？
- 哪些内容明确不做？
- 输入、输出和时点是什么？
- 用什么数据、基线和指标证明有效？
- 哪些决策必须由人确认？
- 怎样回滚？

## 3. Implement：按契约实现

先修改 schema、接口或 ADR，再修改实现。计算组件只产生结构化结果，LLM 只能消费这些结果并生成解释。

实现期间保持任务边界；发现相邻需求时记录到 `state/OPEN_QUESTIONS.md`，不顺手纳入。

## 4. Human Review：用人的判断修正方向

人工重点检查：

- 产品是否真的帮助理解趋势，而非伪装成喊单工具
- 传统概念的翻译是否克制且可检验
- 解释是否遮蔽数据缺口或模型冲突
- 风险语言是否容易诱导过度交易

## 5. Adversarial Review：异质视角复核

让另一个模型、Agent 或人站在反方审查：

- 是否存在更简单的解释？
- 是否重复计算了同一来源的证据？
- 是否用了发布时尚不可获得的数据？
- 概率是否来自模型，还是被语言模型“润色”出来？
- 在什么市场状态下会失效？

评审意见分为 `must-fix`、`follow-up`、`accepted-risk`。

## 6. Validate：通过质量门

至少运行：

```bash
make validate
```

业务实现还要运行本模块测试、时间回放和基线比较。校验失败时，不得用文档声明替代修复。

## 7. Record & Ship：保存可接续状态

完成后：

1. 在任务文件记录结果和验证。
2. 更新 `state/PROJECT_STATE.md`。
3. 有持久决策时补充 ADR，并在 `state/DECISION_LOG.md` 登记。
4. 创建一个主题明确的提交与 Draft PR。
5. PR 描述说明变更、动机、验证和残余风险。
